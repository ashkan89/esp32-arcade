# Verification results

Verification targets classic ESP32-WROVER N16R8, Arduino-ESP32 2.0.17 / ESP-IDF 4.4.7,
Espressif32 PlatformIO 6.10.0, TFT_eSPI 2.5.43 and ArduinoJson 6.21.5.
Run `python scripts/verify.py` to build both environments, execute host tests, regenerate
the actual-renderer preview and package checked release assets. Machine-readable build sizes
and binary hashes are saved in `test-results/firmware-summary.json`.

Both complete-feature `release` and `debug` firmware builds pass. The application is approximately
1.25 MB (release) / 1.38 MB (debug), within each 3 MB A/B slot. Static internal RAM is approximately
60.9 KB; this excludes runtime task stacks, Wi-Fi/TLS heap, PSRAM buffers and banked memory.
The debug build adds runtime profiling output. TFT_eSPI emits its expected no-touch-CS warning;
this hardware has button input and no touch controller.

Host coverage includes **2,000,000 simulation ticks** across 50 games at all four difficulties
and thousands of game-over/restart cycles. Tests cover collision geometry,
fixed-step timing, rollover, input suppression/repeats, CRC corruption at every saved byte,
settings/score migration, favorites, menu/pause lifecycle, shooter weapons/boss/rock splitting,
brick collisions, snake movement/food placement, safe road rows, flap edge behavior, grid merging,
mine adjacency/first-click safety, color run detection, crate-puzzle completion/undo/reset,
hard-drop behavior, release version/repository/hash validation, and guarded renderer clipping.
The graphical refresh also checks that reduced effects freeze menu decoration, enabled
effects animate without changing selection, and procedural artwork respects RGB332 guard bytes.
Focused checks cover all fifty campaign terminal states, twelve-stage lifecycle/pause behavior
for the new games, actual boss damage and objective rules, consumable recovery, armor/guard
behavior and 1,080 generated warehouse solution replays (four difficulties × 30 seeds × nine later stages).
Difficulty regression checks cover all four saved modes, settings cycling and wraparound,
Nightmare run initialization, increasing shooter/road pressure, faster snake movement,
decreasing invulnerability windows, mine density with first-open safety, and puzzle move budgets.
These use controlled states to test rules; they are not fifty human playthroughs or a claim
that all difficulty settings have been tuned on physical hardware.
Host compilation uses real pure C++ modules, not Arduino mocks. Logs are retained in
`test-results/host-build.log`, `host-tests.log` and `firmware-builds.log`.

Release packaging checks both the Sky board/version marker and historical OTA compatibility
marker, classic-ESP32 image header,
16 MB flash header, 3 MB size limit, and actual A/B/otadata partition table before producing
the manifest. The pinned SDK's configuration enables rollback and PSRAM bankswitching;
the firmware links the application's `verifyRollbackLater` override, the SDK certificate
bundle and himem APIs. These are build/link checks, not physical bootloader recovery tests.

The preview at `artifacts/console-preview.png` is generated by the actual game renderer and
includes all 50 games, launcher, menus, a final boss and the victory screen. Native code is compiled with warning checks.
`artifacts/menu-preview.png` isolates console screens, including boot, settings and scores,
for feed-independent UI review at the device's actual pixel dimensions. The new pixel
assets and menu backdrops still need physical display and frame-time acceptance checks;
the earlier hardware results below precede this graphical refresh.
Address/undefined sanitizers were not available in the installed Windows MinGW toolchain;
the host script supports `--sanitize` when a suitable GCC/Clang/MSVC runtime is installed.
The release workflow runs address and undefined-behavior sanitizers on Ubuntu before publishing.

A code-only Graphify structural audit was kept in ignored `.cache/architecture`; its graph
contained 1,350 nodes and 1,631 edges without dangling or collapsed edges. Its parser cannot
fully extract the macro-driven registry, which is instead checked by both real firmware builds
and native catalog tests. Generated graphs are development caches, not shipped firmware sources.

On 2026-10-11, release firmware was uploaded and verified on COM5. The device reported
16 MB flash, 8 MB physical PSRAM, 3,932,159 bytes of mapped PSRAM heap, and allocation of
40 banked-history slots. Boot health checks passed; a 35-second serial capture contained no
errors, aborts or repeated resets (`artifacts/bootloop-final.log`, local ignored log).
Full-frame SPI transfer measured approximately 74.6 ms; the configured 30 FPS request cap
does not imply 30 FPS for full-screen redraws.

The Wi-Fi setup fix was also flashed through COM5 on 2026-10-11. The generated AP key now
uses uppercase hexadecimal, matching the display's uppercase-only font. Release and debug
builds passed, and host tests passed 1,604,048 assertions including setup-key regression checks.
Serial monitoring confirmed an AP client joined, received a DHCP address, and requested the
setup page (`test-results/serial-wifi-fix.log`). Captive-probe paths use the redirect fallback;
the pinned WebServer logs "request handler not found" before executing this fallback.
The same session saved settings and subsequently connected to the configured Wi-Fi network
and synchronized its clock. A release check exposed IDLE0 watchdog starvation by the HTTPS
worker; its priority now matches the idle task so synchronous TLS work can be time-sliced.
The final release/debug builds passed and final firmware booted successfully on COM5.
Its first release-check attempt returned a TLS connection EOF without a watchdog reset
(`test-results/serial-wifi-final.log`). A handshake trace then measured 8.3 seconds verifying
GitHub's ECDSA certificate chain, followed by approximately four seconds of key-exchange work;
the peer had closed the connection before sending its final handshake response.
The HTTPS trust callback now selects TLS 1.2 ECDHE-RSA/AES-GCM suites and P-256 while
retaining the SDK CA bundle, certificate validity checks, and hostname verification.
On COM5, certificate verification dropped to 650 ms and GitHub returned HTTP 200 after
3,897 ms; the console correctly reported current firmware up to date
(`test-results/serial-https-rsa.log`). Both TLS failure details and HTTP timing are logged
without credentials. Debug builds also trace handshake stages and stack headroom.
The normal release build was then flashed to COM5 and confirmed healthy; its own release
check returned HTTP 200 in 3,927 ms with the same up-to-date result
(`test-results/serial-https-release.log`). The new TLS configuration was also verified from
the host against all four allowed GitHub download/redirect hostnames with certificate checks enabled.

The initial firmware repeatedly aborted before setup because the SDK's himem constructor
queried PSRAM before Arduino initialized it. `scripts/defer_himem.py` links a project-local
SDK object with the automatic constructor disabled, and `FrameHistory::begin()` explicitly
initializes himem after the PSRAM checks. A build check inspects the linked constructor table
to prevent this startup regression. The installed SDK is unchanged. A 64 KB coredump partition
was added after both OTA slots, and absent optional NVS keys are checked before reading them.

GPIO levels, physical display output, achieved FPS/latency, audio, Wi-Fi/HTTPS, history
capture/playback, flash power-loss behavior and OTA rollback still require the checks in
`docs/HARDWARE_CHECKLIST.md`.
The release's eight-second acceptance checks ensure allocation and UI progress; they cannot
prove that physical colors, every switch, sound or the radio operate correctly.
